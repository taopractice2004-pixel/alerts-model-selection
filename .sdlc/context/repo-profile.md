# Repository Profile

- Repository mode: `MODE_C_EXISTING_PROJECT`
- Product: AlertService – alert management microservice (create/list/update/deactivate/delete
  alerts, paged + filtered listing, summary counts, liveness/readiness health checks)
- Primary stack: ASP.NET Core Web API on .NET 8 (`net8.0`), C#, EF Core 8 + SQL Server, Serilog,
  Swashbuckle (Swagger), xUnit + Moq + EF Core InMemory/Sqlite for tests
- Repository shape: single Visual Studio solution (`AlertService.sln`) with layered class
  library projects plus two xUnit test projects
- Shared build/runtime settings: `Directory.Build.props` sets `TargetFramework=net8.0`,
  `ImplicitUsings=enable`, `Nullable=enable`, `TreatWarningsAsErrors=false` for every project;
  `dotnet-tools.json` pins local tool `dotnet-ef` 8.0.31 (`dotnet tool restore` required)

## Architecture

- Layering: `AlertService.API` (HTTP/composition root) → `AlertService.DTO` (request/response
  contracts) → `AlertService.Common` (shared enums/constants); API also depends on
  `AlertService.Data` (repository interfaces) → `AlertService.Models` (domain entities) →
  `AlertService.Common`; `AlertService.Data.SQL` implements `AlertService.Data` via EF Core and
  is referenced only by API for DI registration (`AddSqlDataAccess`)
- Entry points / composition roots: `AlertService.API/Program.cs` (top-level statements; exposes
  `public partial class Program` for `WebApplicationFactory<Program>` integration tests)
- User-facing or external interfaces: `AlertService.API/Controllers/AlertsController.cs`
  (REST endpoints under `/api/alerts`), health endpoints via
  `AlertService.API/Extensions/HealthCheckEndpointExtensions.cs` (`/health/live`, `/health/ready`)
- Business logic locations: `AlertService.API/Services/IAlertService.cs` (contract) and
  `AlertService.API/Services/AlertManagementService.cs` (implementation: sets `CreatedDate` from
  injected `TimeProvider`, trims input, preserves `CreatedDate` on update, maps not-found to
  null/false for the controller to turn into 404)
- Data / integration boundaries: `AlertService.Data/Interfaces` (`IAlertRepository`),
  `AlertService.Data.SQL` (`AlertDbContext`, `Configurations/`, `Repositories/`, `Migrations/`,
  `Extensions/` for `AddSqlDataAccess` / `ApplyMigrationsAsync`)
- Runtime / infrastructure notes: Serilog bootstrap + request logging (health-check paths logged
  at Debug), global `ExceptionHandlingMiddleware` turns unhandled errors into 500
  `ProblemDetails`, enum `Severity` serialized as string via `JsonStringEnumConverter`

## Build And Run

- Install / restore dependencies: `dotnet tool restore` then `dotnet restore`
- Build / compile command: `dotnet build` (solution: `AlertService.sln`)
- Test command: `dotnet test`
- Lint / format command: `NOT_CONFIGURED` (no `.editorconfig`/analyzer/lint script discovered)
- Run main app locally: `dotnet run --project AlertService.API --launch-profile https`
  (Swagger UI at `https://localhost:7080/swagger` in Development)

## Data And Operations

- Primary data store: SQL Server (LocalDB, Express/Developer, or Docker), accessed via EF Core
  through `AlertDbContext` in `AlertService.Data.SQL`
- Environment/config notes: connection string `ConnectionStrings:AlertDb` in
  `AlertService.API/appsettings.json`; `Database:ApplyMigrationsOnStartup` flag (true in
  `appsettings.Development.json`) applies EF migrations at startup
- Operational assets: `database/01_CreateDatabase.sql` (creates `AlertServiceDb`),
  `database/02_AlertServiceDb_Migrations.sql` (idempotent script generated from EF migrations);
  logs written to console and `AlertService.API/Logs/alertservice-<date>.log`
