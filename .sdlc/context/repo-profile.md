# Repository Profile

- Repository mode: `MODE_C_EXISTING_PROJECT`
- Product: AlertService — alert-management microservice (CRUD + query/summary over alerts)
- Primary stack: C# / .NET 8, ASP.NET Core Web API, EF Core 8 (SQL Server), Serilog, xUnit + Moq
- Repository shape: Single .NET solution (`AlertService.sln`) with layered projects
- Shared build/runtime settings: `Directory.Build.props` (net8.0, `ImplicitUsings=enable`,
  `Nullable=enable`, `TreatWarningsAsErrors=false`)

## Architecture

- Layering: API/HTTP + business services → DTO → Common; API → Data (interfaces) → Models →
  Common; Data.SQL implements Data. Service layer depends only on `IAlertRepository`.
- Entry points / composition roots: `AlertService.API/Program.cs` (DI, Serilog, middleware,
  migrations, health checks); `AddSqlDataAccess(configuration)` registers Data.SQL.
- User-facing or external interfaces: REST API `AlertService.API/Controllers/AlertsController.cs`
  (`/api/alerts` CRUD, `/api/alerts/summary`, deactivate); health probes `/health/live`,
  `/health/ready`; Swagger UI.
- Business logic locations: `AlertService.API/Services/AlertManagementService.cs`
  (`IAlertService`) — sets `CreatedDate` via injected `TimeProvider`, trims input, logging.
- Data / integration boundaries: `AlertService.Data/Interfaces/IAlertRepository.cs` abstraction;
  `AlertService.Data.SQL` (`AlertDbContext`, `AlertConfiguration`, `AlertRepository`, Migrations).
- Runtime / infrastructure notes: Serilog console + rolling file
  (`AlertService.API/Logs/alertservice-<date>.log`); `ExceptionHandlingMiddleware` → 500
  ProblemDetails; optional migrate-on-startup in Development.
