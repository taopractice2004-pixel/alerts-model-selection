## Summary
Add free-form tagging to alerts: a shared `Tag` entity in a many-to-many relationship with
`Alert`, endpoints to add/remove tags, a tag query filter, and tags in `AlertResponse`.

## Acceptance Criteria
| AC | Criterion |
|---|---|
| AC1 | A `Tag` concept exists with a many-to-many relationship to `Alert`, backed by a new join table and EF migration. |
| AC2 | `POST /api/alerts/{id}/tags` adds one or more tags, deduping case-insensitively, max 10 tags per alert, each tag 1–30 chars. |
| AC3 | `DELETE /api/alerts/{id}/tags/{tag}` removes a tag assignment; returns 404 if the alert or the tag assignment does not exist. |
| AC4 | `GET /api/alerts` accepts an optional `tag` query filter composable with `isActive`, `severity`, date range, and `search`. |
| AC5 | Tags are included in `AlertResponse`. |

## Boundaries & Assumptions
- Primary slice: Alert tagging across controller, service, repository, EF model/migration, and DTOs.
- Out of scope: regenerating `database/*.sql` idempotent scripts; tag listing/rename/standalone management endpoints; UI or frontend changes.
- Assumptions to confirm:
  - `POST /api/alerts/{id}/tags` accepts a JSON body `{ "tags": [...] }` and returns 200 with the updated `AlertResponse` (404 if the alert is missing, 400 on validation failure).
  - `DELETE /api/alerts/{id}/tags/{tag}` returns 204 on success and treats the route tag value case-insensitively.
  - The tag query filter is a single, case-insensitive, exact-match value.
  - Tags are global shared entities: one `Tag` row per unique normalized name, enforced by a unique index and by application-level dedupe.

## Risks
- Medium: new many-to-many plus Include changes the alert read query shape and adds a migration; rollback = revert the touched files and drop the `AddTags` migration.
- Medium: the repository tests use the EF InMemory provider which does not enforce the unique `Name` index or case-insensitive collation, so dedupe and normalization must be enforced in application code, not only in the database.
