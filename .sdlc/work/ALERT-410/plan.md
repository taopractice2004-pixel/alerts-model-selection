# Story ALERT-410 - Alert Tagging

## Story Summary
Let operators attach multiple free-form tags to an alert (new `Tag` concept, many-to-many with `Alert`), add/remove tag endpoints, a composable `tag` filter on list, and tags in `AlertResponse`. | Case: SIMPLE

## Acceptance Criteria
- AC1 - A `Tag` entity with a many-to-many relationship to `Alert` exists, persisted through a new join table created by a new EF Core migration.
- AC2 - `POST /api/alerts/{id}/tags` adds one or more tags to the alert and returns 200 with the updated alert; returns 404 when the alert does not exist.
- AC3 - Tags added via `POST` are deduplicated case-insensitively (against the request and the alert's existing tags), each tag is 1-30 characters, and an alert holds at most 10 tags; violating input returns 400.
- AC4 - `DELETE /api/alerts/{id}/tags/{tag}` removes the tag assignment and returns 204; returns 404 when the alert does not exist or the tag is not assigned to it.
- AC5 - `GET /api/alerts` accepts an optional `tag` query filter that composes with the existing `isActive`, `severity`, `createdFrom`/`createdTo`, and `search` filters.
- AC6 - `AlertResponse` includes the alert's tags.

## In Scope
- New `Tag` domain entity and `Alert`<->`Tag` many-to-many mapping, configuration, and migration.
- Add-tags and remove-tag endpoints, service methods, and repository support.
- `tag` filter on the existing list endpoint and `Tags` on `AlertResponse`.

## Out of Scope
- Listing or managing tags independently of an alert (no tag CRUD endpoints).
- Renaming/merging tags, tag usage counts, or tag-based summary aggregation.
- Pagination or sorting changes beyond adding the `tag` filter.

## Do Not Modify
- `AlertService.Data.SQL/Migrations/**` by hand (generate via `dotnet-ef`; the new migration is added by the tool, not hand-edited).
- `database/**` by hand (regenerated from migrations).
- `standards/**`.

## Implementation Plan

### Contracts
- `POST /api/alerts/{id}/tags`; request body `AddTagsRequest { List<string> Tags }` (1-10 items, each 1-30 chars after trim); responses: 200 `AlertResponse` (with `Tags`), 400 `ValidationProblemDetails` (empty list, item length out of range, or resulting total > 10), 404 (alert not found).
- `DELETE /api/alerts/{id}/tags/{tag}`; `tag` is a non-empty route string; responses: 204 (removed), 404 (alert not found or tag not assigned).
- `GET /api/alerts` request gains optional `tag` (string, max 30 chars); response unchanged shape, items filtered by tag.
- `IAlertService.AddTagsAsync(int id, AddTagsRequest request, CancellationToken) -> Task<AlertResponse?>` (null when alert not found).
- `IAlertService.RemoveTagAsync(int id, string tag, CancellationToken) -> Task<bool>` (false when alert not found or tag not assigned).
- `IAlertRepository.GetAllAsync(... , string? tag = null, ...)` new optional `tag` parameter added before paging params; `IAlertRepository.GetTagsByNamesAsync(IEnumerable<string> names, CancellationToken) -> Task<IReadOnlyList<Tag>>`.
- DTO `AlertResponse.Tags : List<string>` (empty list when none, never null).
- `AlertQueryRequest.Tag : string?` (`[StringLength(AlertConstants.TagMaxLength)]`).
- Entity `Tag { int Id; string Name; ICollection<Alert> Alerts }`; `Alert.Tags : ICollection<Tag>`.
- New `AlertConstants`: `TagMinLength = 1`, `TagMaxLength = 30`, `MaxTagsPerAlert = 10`.

### Behavior Rules
- Tag names are trimmed; comparison and dedupe are case-insensitive (AC3).
- Within a `POST` request, duplicate names (case-insensitive) collapse to one; names already on the alert are ignored, not re-added (AC3).
- Reject the request with 400 when any name is empty/whitespace or longer than 30 chars after trim, or when the resulting tag count on the alert would exceed 10 (AC3).
- Reuse an existing `Tag` row when one with the same name (case-insensitive) exists; otherwise create a new `Tag` so names are shared across alerts (AC1, AC2).
- `AddTagsAsync` returns null -> controller 404 when the alert id does not exist (AC2).
- `RemoveTagAsync` returns false -> controller 404 when the alert does not exist or the named tag is not currently assigned (AC4); removing detaches the assignment only (does not delete the shared `Tag` row).
- `tag` list filter matches alerts having any assigned tag equal (case-insensitive) to the value, and is applied with the existing filters before paging (AC5).
- `ToResponse` maps assigned tag names into `Tags` (stable order, e.g. ordered by name); reads that feed responses include the `Tags` navigation (AC6).
- Log add/remove outcomes with the existing structured-logging style (e.g. "Added {Count} tag(s) to alert {AlertId}", "Removed tag {Tag} from alert {AlertId}"); warn-and-return on not-found like `UpdateAsync`/`DeleteAsync`.

## Dependencies / Risks
- Dependencies: EF Core 8 many-to-many (skip navigations); `dotnet-ef` local tool for the migration.
- Risks: Adding `.Include(a => a.Tags)` to `GetByIdAsync` loads tags on update/deactivate/delete paths - verify existing tests still pass. Case-insensitive match relies on SQL Server's default case-insensitive collation; the `ToLower()` comparison keeps behavior consistent on InMemory/Sqlite test providers.
- Stop points: Schema/migration change requires plan approval (Data Access standard). Generating the migration and regenerating `database/02_*.sql` runs the EF tooling, which is outside pure source edits - confirm before `/implement-story` performs it.
