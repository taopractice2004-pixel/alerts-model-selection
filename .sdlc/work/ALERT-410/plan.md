## Summary
Add tag storage, mutation endpoints, query filtering, and response mapping so operators can organize alerts with free-form tags and filter by them.

## Acceptance Criteria
| AC | Criterion |
|---|---|
| AC1 | Persist tags for alerts through a new Tag concept with a many-to-many schema and migration. |
| AC2 | POST /api/alerts/{id}/tags adds one or more tags, dedupes case-insensitively, limits each alert to 10 tags, and enforces 1-30 characters per tag. |
| AC3 | DELETE /api/alerts/{id}/tags/{tag} removes a tag assignment and returns 404 when the alert or assignment does not exist. |
| AC4 | GET /api/alerts supports an optional tag filter that composes with the existing isActive, severity, date range, search, sorting, and paging filters. |
| AC5 | AlertResponse includes the alert's tags. |

## Implementation Steps
1. Update `AlertConstants`, `AlertQueryRequest`, `AddAlertTagsRequest`, and `AlertResponse` for tag limits, filter input, add-tags payload, and response shape.
2. Extend `Alert`, create `Tag`, and update `AlertMappingExtensions` so tags flow through the domain and DTO layers.
3. Extend `IAlertRepository`, `IAlertService`, and `AlertManagementService` with tag mutation operations and tag-aware query orchestration.
4. Update `AlertsController` to expose `POST /api/alerts/{id}/tags` and `DELETE /api/alerts/{id}/tags/{tag}` on the existing alert surface.
5. Update `AlertDbContext`, `AlertConfiguration`, `TagConfiguration`, and `AlertRepository` for the new many-to-many mapping, query filter, and persistence logic.
6. Create the `AddAlertTagging` migration, refresh `AlertDbContextModelSnapshot`, and regenerate `database/02_AlertServiceDb_Migrations.sql`.
7. Expand controller, service, and repository tests for tag validation, persistence, filtering, response mapping, and not-found behavior.

## Boundaries & Assumptions
- Primary slice: Alert tagging across the `AlertsController`, `AlertManagementService`, `AlertRepository`, and EF Core alert model.
- Out of scope: Dedicated tag administration endpoints outside the alert resource; changes to alert summary behavior or non-tag alert filters.
- Assumptions to confirm: Invalid tag additions return 400 with the existing API validation style instead of introducing a new error contract.

## Risks
- Medium: the feature spans API, business rules, EF mapping, and query composition, so regressions can affect existing alert reads; rollback = revert the tagging files and migration.
- Low: tag filtering must preserve paging and total counts when joins are introduced; rollback = remove the tag filter and eager-loading changes from the repository.
